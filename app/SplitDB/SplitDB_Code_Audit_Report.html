三、高危问题详解

H-01 · 跨季度编辑时旧归档索引作废失效，编辑可能静默不生效

ExternStorage.php:71-123 invalidateArchiveEntry() 按「新 relPath 所在目录」计算 .idx 路径

机理：正文编辑后 write() 用当前季度生成新 .txt 路径，然后调 invalidateArchiveEntry() 去删除旧 .idx 条目。但该方法用 新路径的目录 拼 .idx 文件名，而归档 .bin/.idx 位于原始季度目录。同季度编辑时两者同目录、可命中；跨季度（如 18 个月归档后的老帖被编辑）时，新路径目录下没有 .idx → 提前 return，旧 .idx 条目永不作废。

实测确认：构造「归档在 2026Q2、编辑写 2026Q4」场景，Q2 的 22000.idx 中 22005 条目未被动过（探针输出：old Q2 idx intact? YES）。此时若调用方未同步重写 bucket 行的 extern_path，读取链路将命中旧 .bin 归档 → 用户编辑后看到的仍是旧正文，且无任何报错。

触发条件：① 被编辑正文的归档与编辑发生在不同季度（常见于 18 个月归档机制 + 老帖二次编辑）；② 调用方编辑时未重写 extern_path。修复方向：作废应基于旧路径（或在写入时按「原归档目录」扫描作废），而非仅新路径。

H-02 · 单条巨型 INSERT 的占位符数量依赖编译期 SQLITE_MAX_VARIABLE_NUMBER

SearchIndexStore.php:203-215 writeIndex() 一次性内联全部 token

机理：整篇索引把全部词条放进一条多行 INSERT（每词条 2 个占位符 + 3 个共享参数）。SQLite 的单语句变量数上限由编译期宏决定：默认编译为 999，约 330 词条即触发 too many SQL variables；本机 phpstudy 构建实测上限 32766（约 1.6 万词条）。

实证：本机 SQLite 3.39.2 上限实测 32766；但代码注释宣称兼容 SQLite 3.33 基线、面向低配虚拟主机——这些宿主很可能使用默认编译（上限 999）。中文长文分词可达数千词条，在默认宿主上 整个索引事务回滚 → 发帖/改帖直接失败，且为运行时才暴露。

修复方向：按固定块（如每 200~300 词条）分多条 INSERT，块间共用同一事务。

M-01 · 浏览量计数：APCu 键无 TTL 只减不删 + 先扣后落库

ViewCounter.php:30-33,73-99

① inc() 的 apcu_inc(key,1) 未传 TTL，对不存在键会新建且永不过期；flush() 用 apcu_dec 扣到 0 但从不删除键 → 每个被访问过的主题永久占用一个 APCu 键，键数量随历史访问主题数无限增长（低配宿主 APCu 共享内存压力）。② flush() 先 apcu_dec 再 UPDATE 落库：若落库过程中 DB 抛错回滚，APCu 计数已扣、无法恢复 → 该批浏览量丢失。③ 30s 节流文件读写非原子，多 FPM worker 下节流形同虚设（写锁串行化可避免重复计数，但节流本意失效）。

四、中危问题摘要

编号问题影响 / 建议
M-02DBFactory::closeAll() 内 foreach + $pdo=null 是无效代码（foreach 传值拷贝，置 null 不影响数组），真实清理靠 $connections=[]；evictLRU() 淘汰时未检查句柄是否处于活动事务误导性死代码建议删除；极端场景（请求内开多库 + 事务句柄空闲超 7 个）可能静默回滚未提交事务——概率低但建议淘汰前检查 $pdo->inTransaction()
M-03write() 的 Windows 兜底（unlink 旧目标再 rename）基于过时前提——实测 PHP 8.2 Windows 下 rename() 可原子覆盖已存在文件；且 write() 有兜底、invalidateArchiveEntry() 无兜底，两处不一致兜底分支若真触发（旧版 PHP），删旧+改名窗口内读取会短暂失败/读空；建议统一并删除过时注释
M-04队列表只增不删：done/failed 永不清理，queue_*.sqlite 无限增长；QueueConsumer 每个实例绑定单个队列文件需 purge 策略；部署时必须每队列文件各起一个 worker，否则 queue_1/2 积压永不消费（文档未明确）
M-05recoverTimeout() 只在「无 pending 任务」（空闲）时调用高吞吐下崩溃任务卡在 processing 无法及时回收重试；建议每 N 次循环或按时间戳节流调用
M-06read 端 apcu_store('extern_'.$id, …) 可能在 write 端已写入新值后，用旧内容覆盖缓存600s 窗口内读到旧正文的窄竞态；建议写端缓存键带版本或写后延迟刷新读缓存
M-07countTargets() / searchByTokens() 对高频词把所有去重 target 装入 PHP 数组（O(结果集)）超大结果集内存压力；建议按 take 分页或用 SQL 端去重计数
M-08过渡期三份真相并存：business.threads/posts（退役中）、分片桶 topic/reply、main_index 索引，同步完全依赖外部调用方任一路径漏写即静默漂移；建议明确「唯一真相源」并尽早退役 transitional 表，或加启动时对账

五、低危与提示

编号问题
L-01data/ 防护文件只在 Apache/IIS 生效；Nginx 需外部 nginx-server.conf deny、Apache 需 AllowOverride 开启，否则 data/ 下 SQLite（含密码哈希/会话）可被 HTTP 直下——上线前需按部署环境核对

L-04Schema::bucketFromPath 对不存在的归档桶会静默建空库并建表 → 读到空数据而非报错，掩盖真实缺失
L-05seedDefaults 固定 id + INSERT OR IGNORE：管理员删除默认版块/分类后重跑 bootstrap 会被复活
L-06多处 mkdir / file_put_contents 未加 @，磁盘满/权限问题时冒 PHP warning（与周边 @ 风格不一致）
L-07extern 正文写 tmp + rename 未 fsync；断电可能丢最近正文写入（SQLite 侧有 WAL 兜底，正文文件无）
L-08CountingPDO 全量计数经页脚“总 SQL”展示，为内部遥测轻微信息暴露（无安全实质影响）

六、安全专项结论

未发现可直接利用的漏洞：全部用户输入走参数绑定；唯一字符串内联为 int 白名单（deleteTargets 已 intval）；bucket_path / extern_path 均经正则白名单约束后拼路径，无注入与目录穿越面；PDO 持久连接红线已禁止；WAL + busy_timeout + synchronous=NORMAL 配置合理。
关注点结论
SQL 注入无（全参数化 + int 白名单内联）
路径穿越无（正则白名单：\d{4}Q\d / \d+）
存储型 XSS引擎按 HTML 原样存取 extern 正文（ExternStorage），XSS 防线完全在应用层输出侧——本目录无法验证；建议对正文输出做白名单过滤/转义，属集成红线
数据目录直下部署依赖（见 L-01），Apache/IIS 有自动防护，Nginx 需外部配置
会话/密码哈希sessions 独立库、用户密码哈希在 business.sqlite，均在 data/ 下受目录防护保护
计数/遥测页脚“总 SQL”轻微信息暴露（L-08），无实质风险

七、架构与设计评价

做得好的地方：
  • 事务边界严谨：IDGenerator 用 BEGIN IMMEDIATE 规避 PDO-SQLite 混用 commit 的 “no active transaction” 陷阱，并有明确注释；对 SQLite 3.33 基线的兼容取舍清晰。
  • 索引设计有实测依据与回退记录（如撤销覆盖索引避免列表查询 TEMP B-TREE 回归、uid 复合索引防规划器误选），说明走过真实调优。
  • 降级路径完备：无 APCu 静默降级、.bin/.idx 缺失回退 .txt、正文 16MB 长度防御、队列防挂起 CAS + 超时恢复。
  • 幂等建表 + PRAGMA 补列策略完整，老库升级路径安全；目录防护文件覆盖 Apache/IIS/Nginx 三场景。
  • 命名规范、注释质量高（含白皮书章节引用、修复日期标注），可维护性好。
维度评价
扩展性季度 + 哈希双层分片、读取以 bucket_path 为准的零迁移扩容设计合理；扩容仅影响新写入，旧桶冻结是刻意取舍
写放大全局 ID 单锁（global_id.sqlite BEGIN IMMEDIATE）为全站写入串行点，低并发社区可接受；高并发下是吞吐上限（架构提示）
队列模式默认 queue_mode=sync，即“异步架构”默认同步执行；cli/cron 模式才真正异步（最终一致性）——需在文档中明确预期
连接池8 句柄 LRU 为单请求级（非持久连接），请求内多库触顶会重复开关文件；对常规页面负载无影响
